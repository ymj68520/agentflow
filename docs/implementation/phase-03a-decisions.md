# Phase 3A Decisions — Core Semantic Type Universe

> 本文件记录 Phase 3A 中冻结文档未唯一确定、但实现必须做出的设计决定。
> 每条都是显式 Decision；除非改变已冻结的 golden bytes，否则无需重新开放。

| # | 主题 | 决定 | 理由 |
|---|---|---|---|
| D-1 | Machine vs Workflow primitive 分离 | Workflow 语义原语宇宙**冻结为 9 个**：`unit/null/bool/int64/decimal/string/bytes/timestamp/duration`（`value_no` 1..9，顺序即此序）。`int32/uint32/uint64/float64` 是 machine-only，在任何 workflow 类型入口一律拒绝。唯一闸门是 `SemanticPrimitiveType::try_from_keyword`。 | 任务 §四/§五/§六。AFIDL machine primitive 回答"机器对象如何表达字段"，workflow primitive 回答"用户 workflow 中的值可以是什么"——两者必须分开；`field_no: uint32` 合法，但 `uint32` 不能作为业务值类型。 |
| D-2 | SemanticTypeRef → 索引化 type DAG | 不采用自递归 AFIDL。改用 `SemanticTypeNode` 表：`variant SemanticTypeNodeBody { primitive, schema, list, map_string, option }`，其中 container 三个 case 引用 `SemanticTypeId`。 | 任务 §一百零七/§一百零八 推荐方案。AFIDL1 Phase 2A 禁止 recursive NamedRef（§一百零六 禁止为此外解除）；索引 DAG 可表达任意有限嵌套（`option<list<map<string,T>>>`），且不修改 ACE1、不弱化 AFIDL 限制。 |
| D-3 | Type DAG 不引入 union/Any | 不新增 `union<T,U>` / `one_of` / `Any` / `Json` / `Dynamic` / `Unknown` / `Object`。workflow union 必须用 AFIDL variant schema 表达。 | 任务 §十四/§十五。 |
| D-4 | `SemanticTypeRef` 采用 DAG 索引而非嵌套结构 | `ValueSlot.type`、`ExpressionDef.result_type`、`ListConstruct.element_type`、`MapConstruct.value_type`、`OptionNone.inner_type` 全部使用 `SemanticTypeId`，而非每处内联 type 结构。 | 任务 §一百一十二 推荐。同一语义类型在文档中只定义一次。 |
| D-5 | `ResourceSlot.requirement_type` 用 `TypeSchemaRef` 而非 `SemanticTypeId` | 资源需求 pin 的是 **contract schema**，不是普通值类型，因此不进入值类型 DAG。 | 任务 §五十六/§一百一十三。 |
| D-6 | DigestRef 的 AFIDL 表示 | **新增 `agentflow.semantic.core@1` 并在其中定义唯一一次 `DigestRefValue { algorithm, domain, hex }`**；不新建 `agentflow.core.identity@1`。 | 任务 §九 允许两种方案之一并要求记录 Decision。选择在 semantic-core 内定义，因为本阶段只有它需要，且能避免为一个 3 字段 record 引入新 specification family（减少 surface）。校验规则：`algorithm == "sha256"`、domain ∈ 冻结 HashV1 registry（对 `TypeSchemaRef` 必须恰为 `type-schema`）、hex 为 64 位小写十六进制。**禁止裸 `digest: string`**。 |
| D-7 | `TypeSchemaRef` 三段一致性 | validator 必须同时验证 `specification_id` 语法、`type_name` 语法、identity 存在于显式 `TypeSchemaUniverse`、且 pinned digest == 该 schema 的实际 canonical digest。仅"digest 格式正确"不够。 | 任务 §十一。 |
| D-8 | 无 latest-resolve | 不使用 Registry latest 解析：`TypeSchemaUniverse` 是显式只读输入（测试中由 AFIDL compile output 构建），`TypeSchemaRef` 永久 pin 其 digest。 | 任务 §十二/§六十七/§六十八。 |
| D-9 | Alias 在语义层展开为目标 | `alias UserId = string` 的语义类型即 `primitive:string`（alias 的 nominal 身份体现在 `TypeSchemaDigest` 中，不体现在值类型）。Record/variant/enum 则是 `schema:<identity>@<digest>` 叶子。 | 值层：alias 不产生不同的值表示（Phase 2A D-10 已确立 alias identity ≠ target identity，但那是 *schema* 身份）。语义层若保留 alias 名义身份会导致 `UserId` 与 `string` 的 slot 无法互相赋值，而两者的 ACE1 字节完全相同。 |
| D-10 | PrimitiveConstant 无冗余 type 字段 | `PrimitiveConstant` 的 case 1:1 映射 `SemanticPrimitiveType`；**不含** machine-only primitive case；bytes payload 为 canonical unpadded base64url。 | 任务 §二十八/§二十九。case→type 唯一映射使得保存 type 是冗余；machine-only case 在类型层即不可表示（语料 `constant/machine-only-case` 的 `rejected_at` 为 `deserialize`，即拒绝发生在解析期而非校验期）。 |
| D-11 | 表达式闭集 15 项 | 实现 `constant / value_slot / record_construct / variant_construct / enum_value / list_construct / map_construct / option_none / option_some / field_get / equals / not / and / or / if_then_else`。**不实现**算术（add/sub/mul/div/mod）、字符串拼接、regex、索引、`match_variant`/`is_case`/`unwrap_case`。 | 任务 §三十四/§三十五/§八十四。这些都会引入 overflow、decimal 算术、错误语义、locale 或 runtime failure；本阶段表达式必须"well-typed → total"。 |
| D-12 | `and`/`or` 为二元 | `and(left, right)` / `or(left, right)`，不是 n 元。 | 使 ACE1 字节完全确定（n 元列表在规范化时可能重排操作数，改变短路语义的精神）；二元形式无歧义。 |
| D-13 | `equals` 可比较类型限制 | Phase 3A 只允许 **primitive 类型** 与 **enum schema**；record/list/map/option 的深比较推迟（`type_not_comparable`）。 | 任务 §三十六。深相等需要定义递归结构与循环引用的语义，超出本阶段。 |
| D-14 | Record/variant/enum 选择用编号 | `record_construct` 与 `field_get` 按 `field_no` 选择；`variant_construct` 用 `case_no`；`enum_value` 用 `value_no`。name 仅作值编码 key。 | 任务 §四十四/§四十五/§四十六/§四十七/§四十八。编号是 durable schema ABI，名称是 ACE1 value encoding key——两者职责不同。 |
| D-15 | `option_none` 必须携带 inner_type | `OptionNoneBody { inner_type }`；`option_some` 从 payload 推导 `option<T>`，不另存 inner type。 | 任务 §五十一/§五十二。`None` 无 payload 可推导。 |
| D-16 | `result_type` 为冗余但强制一致 | `ExpressionDef.result_type` 保留作 ABI clarity，但 validator 必须要求 `derived_type == declared result_type`，否则 `expression_result_type_mismatch`。 | 任务 §五十三。 |
| D-17 | 表达式为 DAG，允许前向引用 | 表达式进入 `ExprTable` 按 id 索引，引用其它表达式用 id；前向引用合法；自环/双节点环/更长环一律拒绝（`expression_cycle`）。 | 任务 §三十九/§四十/§八十七/§八十八。共享子表达式不复制；source order 不决定可见性。 |
| D-18 | Map key 规则在**校验期**执行 | `map_construct` 的 key 在 validator 中 NFC 规范化、检测规范化后重复（`duplicate_normalized_map_key`）、按 unsigned UTF-8 字节排序；不推迟到 value encoding。 | 任务 §八十六。 |
| D-19 | 四 namespace 独立 + Rust newtype | `SemanticTypeId` / `ValueSlotId` / `ExpressionId` / `ResourceSlotId` 均为独立 nominal 类型（Rust newtype，底层 u32）。数字相同不代表同一对象。`0` 可表示但在 validator 中拒绝；不发明 `UINT32_MAX reserved` 等额外规则。 | 任务 §五十八/§五十九/§六十四/§六十五。 |
| D-20 | `ValueSlot` 只定义 identity + type | 本阶段不定义 `ValueOrigin` / `ValueProducerRef` / `RunParameterRef` / `ComputationOutputRef`。producer 关系留 Phase 3B dataflow。 | 任务 §二十二～§二十四/§六十二/§六十三。提前定义会牵出 RunParameter/admission 完整规范层。 |
| D-21 | `SemanticCoreDocument` 是测试/校验容器，**不是** `SemanticIRDocument` | 定义 `SemanticCoreDocument { types, values, expressions, resources }` 于 normative schema 中（4 个 list 字段），明确不承诺为最终 Semantic IR 文档；不含 body/control/dataflow，无 document digest。 | 任务 §九十一 允许 test harness 对象；§七十三 明确本阶段不定义 SemanticIRDocument digest。放进 normative schema 使 AFIDL 完整描述本阶段全部机器对象，且未来 Semantic IR 可直接复用这四个表。 |
| D-22 | Canonical ordering 先进入 validator | types/values/expressions/resources 在 canonical model 中按 id 升序；source order 不进入 identity。虽无 document digest，规则已冻结以供 Phase 3B 直接复用。 | 任务 §七十二/§七十三。 |
| D-23 | Bounded lowering | 实现静态类型检查器（`infer_expression_type`）**并**实现 lowering 到 ACE1 `(Shape, Value)` 以冻结 golden bytes。`value_slot` 的 lowering 需要显式 binding（Phase 3A 无 producer），未提供时返回 `value_slot_not_bound`。 | 任务 §八十一 允许"pure deterministic in-memory evaluator"用于 golden testing；§六十六 强制真实类型检查器。降级值是普通 ACE1 字节，**不新增 Hash domain**。 |
| D-24 | 不新增 HashV1 domain | 不引入 `semantic-type` / `semantic-expression` 等域；类型身份来自 `TypeSchemaDigest`，语义对象是普通 ACE1 对象。AFIDL corpus revision 3 为纯 additive。 | 任务 §十六/§一百/§一百零四/§一百零五。 |
| D-25 | `af-semantic` 不依赖 `af-spec` | 依赖方向 `af-core ← af-idl ← af-semantic`，`af-spec` 是独立工具链分支。语义模型不需要 rules.json / abi-numbers.json 即可工作。 | 任务 §七十六/§七十七。由 `static_surface` 测试强制。 |
| D-26 | **不扩展 `SpecificationKind` 枚举** | 尽管新增了 semantic 语义文档，**不**给 `SpecificationKind` 加 `semantic_spec`。该文档登记为既有的 `schema_language`。 | 关键：`SpecificationKind` 是 `agentflow.spec.registry@1` 的冻结 enum，扩展它会使 `SpecificationKind` 与 `SpecificationRegistryEntry` 两个 Phase 2B digest 漂移，直接违反任务 §一百零四「旧 AFIDL digest 全部不变」。`semantic_spec` 作为 future kind 记录于此 Decision，留待一个允许 additive registry evolution 的阶段。生成器已回退该改动。 |
| D-27 | `machine-primitives` 不参与 ABI numbering | ABI registry 从 `spec/idl/specification-registry.afidl` 与 `spec/idl/semantic-core.afidl` 自动派生（由 registry 生成器中的独立 AFIDL 实现扫描）；`machine-primitives.afidl` 只有 alias，无编号，不产生行。 | 任务 §三十二（Phase 2B）延续：alias 无编号。派生而非手写，使生成器成为唯一事实来源并消除手抄漂移。 |
| D-28 | 语料 `rejected_at` 字段 | negative case 标注拒绝层：`check`（文档可解析，validator 拒绝）或 `deserialize`（文档在受限类型模型中不可表示）。 | 闭集类型模型使 machine-only constant case 在**解析期**即不可表示——这本身是更强形式的拒绝。测试据此分别断言，避免为了"统一"而弱化类型模型。 |
