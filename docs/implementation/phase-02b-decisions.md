# Phase 2B Decisions — Normative Registry

> 本文件记录 Phase 2B 中冻结文档未唯一确定、但实现必须做出的设计决定。
> 每条都是显式 Decision；除非改变已冻结的 golden bytes，否则无需重新开放。

| # | 主题 | 决定 | 理由 |
|---|---|---|---|
| D-1 | RuleId 语法 | `AF-<AREA>-<4DIGIT>`（恰好 4 位、零填充、0001..9999；`0000` 非法）。AREA 语法 `[A-Z][A-Z0-9]*` 且必须命中 `spec/tables/rule-areas.json`。descriptor 的 `area` 字段必须同时（a）属于封闭表、（b）与 RuleId 内嵌 area 段一致。 | 任务 §九 提供两种位数，要求本阶段选定唯一格式；4 位与现有 corpus 案例量级匹配。area 双重校验堵住"rule_id 与 area 字段不一致"的漏洞。 |
| D-2 | Rule Area 集合 | 本阶段登记 `ACE1 / AFIDL / DIGEST / REGISTRY / SPEC` 五个。允许表中存在暂无规则的 area（如 WIDGET 在 corpus fixture 中）。 | 任务 §十一 只登记真实存在者；area 的存在表示"该领域进入 normative source 阶段"，与是否已有规则解耦。 |
| D-3 | SpecificationKind 集合 | 冻结 7 个：`encoding / digest / digest_domain_registry / schema_language / schema / closed_table / registry`。未采纳建议中的 `conformance_profile / semantic_spec`（尚未物化）。 | 任务 §五 要求最小真实集合；closed enum 扩展需显式决定（本表即为该决定）。`digest`、`schema_language`、`registry` 是本阶段真实存在但建议清单未覆盖的类别。 |
| D-4 | SpecificationId 命名 | 新命名约定 `agentflow.<domain>.<name>@1`；已冻结的 `agentflow.core.machine-primitives@1` **保持不变**（13 个 alias digest 已冻结于 corpus，§四十九 禁止重命名）。`agentflow.idl.afidl@1` 与 `agentflow.idl.type-schema@1` 共享同一 normative source 文件（不同章节）。 | 已冻结 identity 优先于命名美观；两个 schema_language 条目对应同一文档的不同规范层（语言 vs identity 公式），路径共享合法。 |
| D-5 | `schema_digest` 字段暂缺 | specifications.json 的所有条目**均不填** `schema_digest`（可选字段）。模块级语义 digest（SchemaModuleDigest）在 Phase 2A D-5 已 deferred 且本阶段禁止新增 HashV1 domain。drift 防护由三层承担：normative_source 的 ArtifactFileDigest（字节完整性）、AFIDL corpus 的逐类型 digest golden、ABI registry 的编号一致性检查。 | 任务 §八：NO new semantic HashV1 domain。用 `(alg, domain, hex)` 语义 DigestRef 表示模块级 digest 需要新 domain 或复用决定，均超出本阶段授权。 |
| D-6 | ArtifactFileDigest vs DigestRef | 新类型 `ArtifactFileDigest { algorithm: "sha256", hex }` = 文件字节 plain SHA-256，是 **repository tooling identity**；与 HashV1 语义 `DigestRef`（domain-carrying）在 AFIDL schema 中是两个不同的 record，永不互换。 | 任务 §七 的核心区分。 |
| D-7 | rules.json 的 normative_source 形态 | 规则的 normative_source 是纯 `logical_path` 字符串（不带 per-rule content digest）。文件完整性由其所属 specification 条目统一钉住；规则额外要求该路径必须是某个已登记 specification 的 normative_source。 | 47 条规则各自复制文件 digest 是维护灾难；路径→specification 的归属检查已保证规则钉在真实规范上。 |
| D-8 | 锚点机制 | 锚点 = `<a id="..."></a>` 行或 heading slug（md）；AFIDL 源文件的锚点 = 已声明类型名（用 Phase 2A parser 校验）。禁止行号。多条规则可在同一节相邻放置各自锚点；`(path, anchor)` 二元组跨规则唯一。锚点注入是纯增量的规范维护（§四十六），不改变任何 golden bytes。 | 锚点标记"要求所在位置"，粒度由 registry 的 short_statement 承担；二元组唯一防止两条规则退化绑定同一标记。 |
| D-9 | Provisional 标记约定 | frozen 源文件中以下两种为标记：trim 后（剥离 `>` 引用前缀）以 `status:` 开头且续以 `provisional`（大小写不敏感）的行；或以大写 `PROVISIONAL` 起始后跟 `:`/空白/行尾的行。散文中提及 "provisional" 一词（如描述被取代的历史文件）不是标记。 | 任务 §四十三 只要求"frozen source not marked provisional"；现有规范文档的 Status 头包含历史性 "provisional" 措辞，朴素子串匹配会误报。 |
| D-10 | ConformanceCaseId 三形态 | (1) corpus JSON 内已冻结的 `case_id` 字符串原样复用（不重写既有 golden）；(2) 文件型 corpus（parser-invalid）用 manifest 中的 `.afidl` 文件名 stem；(3) `SUITE-<AREA>-<SLUG>` 形式的 suite id，声明于 `spec/conformance/suites.json`（本阶段 1 条：SUITE-DIGEST-DOMAIN-SEPARATION，代表 domain-separation 矩阵 + af-core property test）。校验器扫描 `spec/conformance/**/*.json` 提取 universe。 | 任务 §二十/§二十一：优先复用既有 case_id，不为格式统一重写 golden；§六十五/§六十六：property suite 用稳定 suite id，不引用 Rust 测试函数名。 |
| D-11 | 覆盖率三分类与冻结摘要 | `covered`（refs 非空）/ `intentionally_uncovered`（refs 空 + reason 非空）/ `missing_coverage`（两者皆无，恒为错误）。must/must_not 规则的 intentionally_uncovered 必须列于冻结的 `spec/registry/coverage-summary.json`，否则报错。**测试不断言总数**（避免增长噪音），只断言：missing==0、computed uncovered 集合 == 冻结摘要。当前唯一例外：AF-ACE1-0001（架构不变量，fixture 不可证伪）。 | 任务 §二十二/§二十三/§六十三 的直接实现；§二十四 目标是"验证机制"而非 100%。 |
| D-12 | ABI Registry 历史模型 | 每个 `(schema_family, type_name, number_kind, number)` 只出现**一行**，历史由 `status`（active/reserved/retired）表达，而非多行追加。retired 编号在 scope 内永久绑定其 symbolic_name；reserved 行豁免 schema 对照。retire 只能手工编辑 registry 文件（显式 spec change），校验器只做一致性检查、从不改写。 | 任务 §二十七/§三十/§三十五。单行+状态模型使"编号曾被占用"可机检，避免多行历史的排序/合并歧义。 |
| D-13 | 自举顺序与 authority | 顺序：手工写 `spec/idl/specification-registry.afidl` → Phase 2A compiler（Rust）与独立 Python 实现双方解析 → 20 个 TypeSchemaDigest 冻结进 AFIDL corpus（revision 2，additive）→ 50 个 field/value 编号登记为 abi-numbers.json 的 active 行（携带 first_seen_schema_digest）→ registry JSON 实例由 af-spec 校验。AFIDL source 是唯一 authority；JSON 是实例。**不新增 HashV1 domain**（digest 域仍为 `type-schema`）。 | 任务 §五十二/§五十三/§五十四/§七十一。 |
| D-14 | Registry JSON 的 canonical 字节形态 | 适用于 `spec/registry/*.json`、`suites.json`、spec-registry corpus 的 registry 文件：2-space indent、LF、末尾换行、每层 key 字典序排序——校验器用 serde_json 排序 pretty printer round-trip 逐字节验证。既有 closed tables（hash-domains、afidl-primitives）与既有 corpus 保留各自冻结格式，只做语义检查（重复/排序/格式/drift），不做字节形态检查。数组冻结顺序：specifications 按 specification_id、rules 按 rule_id、abi 按 (schema_family, type_name, number_kind, number)、areas 按 area、suites 按 suite_id；`number_kind` 等枚举按 JSON 字符串排序。 | 任务 §三十七/§三十八。既有文件的字节形态已被各自 corpus 冻结，追溯重排只会制造噪音。 |
| D-15 | af-spec 依赖 serde/serde_json | af-spec 作为 spec tooling crate 允许直接依赖 serde/serde_json（registry JSON 解析是其本职）；不违反 Phase 1 对 af-core 语义路径的依赖原则——af-core/af-idl 的依赖面未变。依赖方向维持 `af-core ← af-idl ← af-spec`。 | 任务 §四十一/§四十二；JSON 解析是 registry 工具链的原生需求，手写 parser 反而引入风险。 |
| D-16 | af-idl corpus_revision 2 | schema-golden 与 type-schema-digest-golden 升至 revision 2（additive：新增 `specification-registry` case，20 个新 digest；旧 case 与旧 digest 逐字节不变——diff 仅 2 行 revision 行）。parser-invalid manifest 是独立冻结制品，保持 revision 1。 | 任务 §七十三/§七十四："新增 Registry AFIDL schema 只新增 digest，不改旧 digest"。 |
| D-17 | spec-check 只读 | `check` 只验证、不改写；错误→非零退出。格式化/生成由显式的独立工具（`tools/gen-registry-instances.py`、`tools/gen-spec-registry-corpus.py`）承担，二者幂等（二次运行零 diff）。 | 任务 §六十一。 |
